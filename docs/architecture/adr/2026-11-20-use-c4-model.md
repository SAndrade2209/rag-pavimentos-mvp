# Document the architecture with the C4 model and diagrams as code in PlantUML

- Date: 2026-11-20
- Status: Accepted

## Context

The MVP needs architecture documentation that:

- Describes the system at several levels of detail: its environment (users and external systems), its containers (applications, services and data stores) and its internal components.
- Uses a common notation for the whole team.
- Lives in the same repository as the code, is versioned with Git and is reviewed in the same pull requests.

Diagrams made in drawing tools are stored as binary or exported files. Their changes cannot be reviewed line by line and they tend to become outdated relative to the code.

## Decision

1. Document the architecture with Simon Brown's C4 model (https://c4model.com) at three levels:
   - C1 Context: `docs/architecture/c4/c1-context.puml`
   - C2 Containers: `docs/architecture/c4/c2-containers.puml`
   - C3 Components: `docs/architecture/c4/c3-components.puml`
2. Do not produce level 4 (code). In an MVP, hand-maintained class diagrams change with every refactoring and their maintenance cost is high. If they are needed, they are generated from the code or the IDE.
3. Write the diagrams as code in PlantUML with the C4-PlantUML library (https://github.com/plantuml-stdlib/C4-PlantUML).

## Attributes gained

- Maintainability of the documentation: plain-text files with readable diffs.
- Traceability: the history of the architecture is kept in Git alongside the code.
- Comprehensibility: each level targets an audience. C1 is also readable by non-technical stakeholders; C2 and C3 target the technical team.
- Consistency: a single notation for all diagrams.

## Attributes sacrificed

- Control over visual design: PlantUML computes the layout of the elements and fine-tuning is limited.
- Accessibility for non-technical people: editing the diagrams requires knowing the PlantUML and C4-PlantUML syntax.
- Code-level detail: without level 4, the mapping between components and classes is not documented in diagrams.

## Consequences

- Rendering the diagrams requires PlantUML (local installation, PlantUML server or editor extension).
- The files include C4-PlantUML from its URL on GitHub (`master` branch). Rendering requires internet access, and a change in the library can alter the diagrams. If stability is needed, pin a published version (tag) in the `!include` URL.
- Every architecture change updates the diagram of the corresponding level. If the change involves a decision, an ADR is recorded.
- The diagrams are not generated from the code: keeping them current depends on reviewing them in every pull request that changes the architecture.

## Update 2026-11-23

- The diagrams now load the C4-PlantUML library that ships with PlantUML (`!include <C4/C4_Context>` and the matching container and component files) instead of the GitHub `master` URL above. With PlantUML 1.2026.10, the `master` version printed deprecation warnings on every diagram; the bundled version (C4-PlantUML 2.14.0) prints none. Rendering no longer needs internet access, and the library version now follows the PlantUML version installed.
- The C3 file (`c3-components.puml`) holds three focused views of the API application (requests and access; loading and data layers; question answering), because a single view with all components and relationships was hard to read.
- Styled copies of the three diagram files are in `docs/architecture/c4/styled/`, for reading and presenting. They show the same elements and relationships as the originals, with one shared look (`style.puml`: colors by module and data layer, Font Awesome icons bundled with PlantUML, rounded boxes), shorter text, numbered steps in the loading and question answering views, and PNG and SVG renders. The loading view leaves out module and database boxes and shows each component's module by color, because the layout engine could not draw that pipeline legibly with them. The diagrams in `docs/architecture/c4/` stay the source of truth: when one changes, its styled copy and renders are updated too, which adds work to every diagram change. Changes are reviewed in the `.puml` files; the renders are generated from them.
