8.3 ADR 3. Client isolation with row-level security

Isolate client data in shared tables with row-level security
Accepted 2026-11-23 · docs/architecture/adr/2026-11-23-isolate-client-data-with-row-level-security.md
What it does

All clients share one database and the same tables. Every row of client data carries a client identifier, and the database itself returns only the rows of the client making the request. The API also filters by client, so one missing filter in the code does not expose another client's data. Permissions between projects of the same client are checked by the API.

Why this option

With 1 to 3 clients expected, a database per client would be manageable, but it multiplies data model updates and backups, sends each request to a different database and turns any later cross-client analysis into a data-copying project. A client that needs its own database can still be moved to one later.

Context

  • The platform supports multiple clients with isolated data (CLAUDE.md). Clients are agencies and airports with government data.
  • Isolation has two levels. Between clients: one client never sees another client's data; this ADR covers it. Between projects of the same client: access is granted per project (UC-07, UC-08) and checked by the API application; not decided here.
  • Client data in the platform database: PCI records per network section and survey year, projects, users, permissions and change history (UC-05, UC-09).
  • Constraint: data and backups stay in the US.
  • Expected clients: 1 to 3 in the first year or two. A client requiring its own database is possible but not likely. Continuum may want to analyze data across clients later, with permission.
  • Attributes involved: security (high), deployability and simplicity (high), recoverability (high), performance (medium).

Options

OptionNotes from the ADROutcome
1. Shared tables with a client identifier; the API filters every querySimplest. A single query that forgets the filter exposes another client's data.Not chosen
2. Shared tables with a client identifier, plus row-level security in the databaseThe database itself returns only the rows of the client making the request, even if the code forgets the filter.Chosen
3. One schema per client in a single databaseStronger separation. Every change to the data model has to be applied to each client's schema.Not chosen
4. One database per clientThe strongest separation, and one client's data can be restored or removed on its own. Every client adds a database to deploy, update, back up and monitor.Not chosen

Decision

  • Every table that holds client data has a client identifier.
  • The database enforces row-level security on those tables: each request sees only the rows of its client. The API application also filters by client, so there are two layers.
  • Per-project permissions (UC-08) are checked by the API application, inside the client's data.
  • Automated tests check that a user of one client cannot read or change another client's data.
  • The database technology chosen for C2 must support row-level security. Both candidates, PostgreSQL and Microsoft SQL Server, do.
  • A client that requires its own database, for example by contract, is moved to one through a new ADR. The client identifier makes its data straightforward to extract.

Attributes

GainedSacrificed
  • Security (high): a missing filter in the code does not expose another client's data, because the database enforces the separation as well.
  • Deployability and simplicity (high): one database to deploy, update and monitor, whatever the number of clients.
  • Recoverability (high): one backup process covers all clients.
  • Recoverability (high), partly: restoring one client's data on its own is harder than with a database per client; it requires restoring a copy and extracting that client's rows. UC-09 reduces the need, since data mistakes are corrected without a restore.
  • Deployability and simplicity, slightly: row-level security policies have to be written and tested for each client table.
  • Performance (medium), slightly: the database applies the policy on every query. The cost is expected to be small with the client identifier indexed.

Consequences

  • C2: the platform database is described as shared tables with row-level security.
  • The database technology ADR must keep row-level security support as a requirement.
  • All clients share one database in the US. A client that needs its data elsewhere needs a separate database (new ADR).
  • Cross-client isolation tests belong to the minimum automated test set (maintainability).
  • Row-level security blocks cross-client queries by default. If Continuum adds cross-client analysis later, it is a separate, explicitly permitted function, decided in a new ADR.

8.4 ADR 4. PCI loading by upload and connection

Load PCI data by file upload and by an automatic connection
Accepted 2026-11-23 · docs/architecture/adr/2026-11-23-load-pci-data-by-upload-and-connection.md
What it does

Opens two ways in for PCI data: CSV and Excel upload for every client, and an automatic connection built only for the funding agency's pavement management system. Every source is converted to one internal format and passes the same UC-05 validation, so new survey years are added, existing values are not overwritten, and each load is recorded with who, when and which source.

Why this option

Upload alone would not meet the funding agency's expectation of an automatic connection. A connection alone would leave out the clients and staff who work from files and spreadsheets.

Context

  • UC-05: PCI data (section, coordinates, PCI, year) come from files and from the client's existing pavement management databases. Each load comes in through a project and is validated: new survey years are added, an existing section and year is reported, not overwritten, and rejected rows are listed with the reason.
  • The funding agency expects the platform to connect automatically to its existing pavement management system. File upload alone would not meet that expectation.
  • New PCI data are loaded yearly or less often per client. Continuum staff and client staff both load data.
  • Clients keep PCI data in spreadsheets as well as in databases, so upload accepts CSV and Excel.
  • Expected clients: 1 to 3 in the first year or two (ADR 3). PDFs and other file types come later; loading must be extensible.
  • The agency's system, its export or API options and its IT rules for connections are not known yet, so the connection method is left to a separate ADR.
  • Attributes involved: security (high), deployability and simplicity (high), data traceability (high), interoperability (medium), extensibility (medium), usability (medium).

Options

OptionNotes from the ADROutcome
1. File upload onlySimplest and safest, but it does not meet the funding agency's expectation.Not chosen
2. Automatic connection onlyLeaves out the clients and staff who work from files and spreadsheets.Not chosen
3. File upload for every client, plus an automatic connection for the funding agency's systemUpload for every client; the connection only for the funding agency's system.Chosen
4. Import API for clientsClients write their own software to send data. Requires development work at each client.Not chosen

Decision

  • Upload: CSV and Excel (.xlsx) files, through the web application, by users with the Load permission on the project (UC-05, UC-08).
  • Automatic connection: built for the funding agency's system only. Another client's system is added only when that client requires it.
  • One validation path: the loading module converts every source into one internal format (client, project, section, coordinates, PCI, year) and applies the UC-05 validation to it. Each source is an input adapter: CSV, Excel and the agency's system now; PDFs later.
  • Column mapping: each client's column names are mapped to section, coordinates, PCI and year once and saved, so later loads reuse the mapping.
  • When it runs: because new data arrive yearly or less often, the connection runs when a user with the Load permission starts it. A schedule is added only if the agency requires one.
  • How it connects (the platform reads the agency's database, reads through the system's API, or the agency's system sends scheduled exports to the platform) is decided in a separate ADR, once the agency's system and IT rules are known.
  • Minimum for any connection method: read-only access limited to PCI data, credentials kept outside the code, and traffic and processing inside the US.

Attributes

GainedSacrificed
  • Interoperability (medium): meets the funding agency's expectation of an automatic connection, and files cover every other client.
  • Data traceability (high): every load, by file or by connection, is recorded with who started it, when and from which source.
  • Extensibility (medium): the input adapter boundary is where other client systems and PDFs plug in later.
  • Usability (medium): Excel files are accepted without conversion, and the agency's data arrive without manual export.
  • Deployability and simplicity (high): one connector to build, test and maintain; coordination with the agency's IT; and it can break when the agency changes its system.
  • Security (high), partly: the platform holds access to one client system, which has to be protected. Upload, by contrast, needs no access to client systems.

Consequences

  • C1 and C2: the client pavement management system stays in the diagrams, with a dashed relationship labeled as the automatic connection for the funding agency, method pending. Its direction is set by the connection method ADR.
  • UC-05: sources are CSV and Excel uploads, plus the automatic connection for the funding agency.
  • C3: the loading module has an input adapter boundary and one shared validation step.
  • [assumption] For connection loads, a copy of the records received is kept, as uploaded files are, so each load can be traced to what arrived.
