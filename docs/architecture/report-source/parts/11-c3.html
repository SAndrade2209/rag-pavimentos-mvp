Part IV. Components

10. C3 Components: inside the API application

C3 opens the API application. ADR 7 splits it into seven modules by business area; each module owns its tables, and other modules use it only through its interface. Three focused views show the components: requests and access, loading and data layers, and question answering. Components that appear in more than one view are described in full in one view only.

10.2 View 1: requests and access

How a request is handled

  1. The web application sends every request to the access guard, as JSON over HTTPS.
  2. The guard checks the sign-in token with the identity service (OpenID Connect).
  3. It reads the user, the client and the project permissions from the platform tables, and sets the client for row-level security.
  4. It denies by default. A request without the needed permission is refused, and the denial goes to the audit log.
  5. A checked request goes to the module that serves it: access management (UC-08), projects (UC-06, UC-07), project and section views (UC-06), load jobs (UC-05), corrections (UC-09) or the query planner (UC-01 to UC-04).
  6. The views read gold; projects read the platform tables; access management writes access and permissions and sends grants and removals to the audit log, which writes its records to the platform tables.

Allowed requests are not logged one by one (ADR 7).

10.3 View 2: loading and data layers

A load, step by step

StepFrom and toWhat happens
1Access guard to load jobsA checked load request (UC-05).
2Load jobs to input adaptersRuns the load as a retryable background job in the same process, tracked in a job table. Running a load again does not duplicate rows.
3Input adapters to file storage, or to the client pavement management systemFor an upload, stores the original file. For the funding agency, reads through the automatic connection (method pending).
4Input adapters to bronzeWrites the raw rows with the load record (who, when, source), read with the column mapping saved per client.
5Load jobs to validation and load summaryStarts the validation of the load.
6Validation to bronzeReads the raw rows.
7Validation to silverWrites validated PCI after the UC-05 checks, and records conflicts with the existing and the new value.
8Validation to gold refreshTriggers the refresh.
9Gold refresh to silverReads the current versions.
10Gold refresh to goldRebuilds the client's serving tables, in the same database transaction as the load.
11Validation to audit logLoad summary: rows added, conflicts, and rejected rows with the reason.
A correction (pink arrows, UC-09)
  • The guard passes a checked correction request to corrections.
  • Corrections writes a new version in silver, with who, when and why, or resolves a load conflict.
  • It triggers the gold refresh, in the same transaction.
  • It sends the change, with who, when and why, to the audit log.
Retention (dotted arrows)
  • The retention job is scheduled and runs in the same process.
  • It deletes original files from file storage when their retention period ends.
  • It asks the audit module to delete expired answer log entries, so each module deletes only its own records.

10.4 View 3: question answering

A question, step by step

StepFrom and toWhat happens
1Access guard to query plannerA checked question, with the client, project and permissions (UC-01 to UC-04).
2Query planner to language model interfaceAsks the model for a query plan built from filters and operations, then validates it.
3Query planner to judgeAsks for a verdict on each validated plan.
4Judge to language model interfaceThe model judges whether the plan answers the question, before the query runs. It receives the question and the plan, never result rows. If the judge rejects the plan, the planner asks for a new one with the judge's reason, up to three plans; after that, the question cannot be answered yet.
5Query planner to query builderThe plan accepted by the judge.
6Query builder to goldA parameterized, read-only query, with the client, project and permissions from the access guard.
7Query builder to answer writerThe query and its results.
8Answer writer to language model interfaceWrites the answer text with the template for the plan's operation, asks the model to reword it, and keeps the reword only if its numbers, survey years and section identifiers match the template text, in the same order.
LogQuery planner and answer writer to audit logThe question, plans and verdicts; then the query, results, texts and check result. Kept for a retention period.

What reaches the language model

The model receivesThe model never receives or does
  • The question.
  • Query plans, to build and to judge.
  • The template text to reword, which holds the answer's figures and section identifiers.
  • Result rows.
  • Access to the database.
  • The client, project or permissions: the API adds them.
  • Writing SQL: model-written queries are not in the first release.

An answered question takes three model calls (plan, judge, reword) and up to seven when the judge rejects plans (three plans, three verdicts, one reword). The building blocks of the query plans and the validation rules are in ADR 6 (8.6).
