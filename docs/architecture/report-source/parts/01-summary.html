Summary

The MVP is a pavement data platform for agencies and airports that manage airport or road networks. Users ask natural-language questions about tabular PCI data (section, coordinates, PCI, survey year) and view PCI in project and section views. PCI data belong to the network and are kept for every survey year; a project is how data arrive and where they are shown. Several clients share the platform, each with isolated data.

Architecture at a glance
  • Two applications: a web application in the browser and one API application, a modular monolith with seven modules.
  • One platform database with three data layers: bronze (loads as received), silver (validated PCI with every version) and gold (serving tables), all under row-level security by client.
  • File storage for the original uploaded files, kept for a retention period.
  • A language model reached through one interface. It builds and judges query plans and rewords answer text, never receives result rows and never reaches the database. Hosted or self-hosted is pending.
  • Sign-in through a hosted identity service (OpenID Connect, MFA, single sign-on, Google Workspace for Continuum staff). Projects and permissions stay in the platform.
  • Two ways to load PCI data: CSV and Excel upload for every client, and an automatic connection to the funding agency's pavement management system (method pending).

Drivers

  • High-priority quality attributes: security; data traceability; deployability and simplicity; recoverability.
  • Constraints: data, backups and language model processing stay in the US; the platform runs on any major cloud provider. An MVP that deploys fast, not sized for millions of users or multi-zone high availability.

Properties that follow from the decisions

  • Every number in an answer comes from database results through a template, not from the model (ADR 6).
  • One client never sees another client's data: API filtering plus row-level security in the database (ADR 3).
  • PCI values are never overwritten: a load conflict keeps the existing value, and a correction is a new version with who, when and why (ADR 7).
  • One deployable API application and one database for all clients, with no separate worker or queue (ADR 3; ADR 7).
