8.1 ADR 1. C4 model and diagrams as code

Document the architecture with the C4 model and diagrams as code in PlantUML
Accepted 2026-11-20, with an update note of 2026-11-23 · docs/architecture/adr/2026-11-20-use-c4-model.md
What it does

Sets how the architecture is described and kept current. The diagrams are plain-text PlantUML files at three C4 levels (context, containers, components), stored in Git next to the code and reviewed in the same pull requests. An architecture change updates the diagram of its level; a decision also gets an ADR.

Why this option

Diagrams made in drawing tools are binary or exported files: their changes cannot be reviewed line by line, and they drift from the code. Level 4 (code) is left out because hand-maintained class diagrams change with every refactoring.

Context

  • The MVP needs documentation that describes the system at several levels of detail: its environment (users and external systems), its containers (applications, services and data stores) and its internal components.
  • It needs one notation for the whole team.
  • It must live in the same repository as the code, be versioned with Git and be reviewed in the same pull requests.

Options

OptionNotes from the ADROutcome
C4 model, diagrams as code in PlantUML with C4-PlantUMLPlain-text files with readable diffs, in Git with the code; one notation; each level targets an audience.Chosen
Diagrams in drawing toolsStored as binary or exported files. Changes cannot be reviewed line by line, and the diagrams tend to become outdated relative to the code.Not chosen
C4 level 4 (code)Hand-maintained class diagrams change with every refactoring, and their upkeep is high in an MVP. If needed, they are generated from the code or the IDE.Not produced

Decision

  1. Document the architecture with Simon Brown's C4 model at three levels: C1 context (c1-context.puml), C2 containers (c2-containers.puml) and C3 components (c3-components.puml), in docs/architecture/c4/.
  2. Do not produce level 4 (code).
  3. Write the diagrams as code in PlantUML with the C4-PlantUML library.

Update of 2026-11-23

  • The diagrams load the C4-PlantUML library bundled with PlantUML (C4-PlantUML 2.14.0 with PlantUML 1.2026.10) instead of the GitHub master URL. Rendering needs no internet access and prints no deprecation warnings; the library version follows the installed PlantUML version.
  • The C3 file holds three focused views of the API application (requests and access; loading and data layers; question answering), because a single view with all components and relationships was hard to read.
  • Styled copies in docs/architecture/c4/styled/ are for reading and presenting: one shared look (colors by module and data layer, icons, rounded boxes), shorter text, numbered steps, and PNG and SVG renders. They show the same elements and relationships as the originals, which stay the source of truth.

Attributes

GainedSacrificed
  • Maintainability of the documentation: plain-text files with readable diffs.
  • Traceability: the history of the architecture is kept in Git with the code.
  • Comprehensibility: each level targets an audience. C1 is readable by non-technical stakeholders; C2 and C3 target the technical team.
  • Consistency: one notation for all diagrams.
  • Control over visual design: PlantUML computes the layout, and fine-tuning is limited.
  • Accessibility for non-technical people: editing the diagrams requires the PlantUML and C4-PlantUML syntax.
  • Code-level detail: without level 4, the mapping between components and classes is not drawn.

Consequences

  • Rendering requires PlantUML: a local installation, a PlantUML server or an editor extension.
  • Every architecture change updates the diagram of its level. If the change involves a decision, an ADR is recorded.
  • The diagrams are not generated from the code. Keeping them current depends on reviewing them in every pull request that changes the architecture.
  • When an original diagram changes, its styled copy and renders are updated too, which adds work to every diagram change. Changes are reviewed in the .puml files; the renders are generated from them.

8.2 ADR 2. Sign-in through an identity service

Delegate sign-in to an identity service
Accepted 2026-11-23 · docs/architecture/adr/2026-11-23-delegate-sign-in-to-an-identity-service.md
What it does

The platform stores no passwords and runs no sign-in of its own. An identity service signs users in, with MFA, single sign-on for clients that require it, and Google Workspace for Continuum staff, and hands the platform a signed token through OpenID Connect. What a signed-in user may do (projects and permissions) is still decided inside the platform.

Why this option

A hosted service gives MFA and single sign-on with no sign-in code to write and no new container. Hosted and self-hosted services both use OpenID Connect, so a later move between them changes configuration, not the platform's code.

Context

  • UC-07: users sign in and see only the projects granted to them; a user without access to any project cannot enter. UC-08: managers grant and remove access per project.
  • Two concerns are often mixed up. Authentication proves who the user is and is decided here. Authorization, what that user may do (projects and permissions, UC-07, UC-08), stays in the platform.
  • Some clients may require their staff to sign in with their own organization's accounts (single sign-on); others may accept accounts created in the platform. Both cases have to be supported.
  • Continuum staff, consultants and administrators, use Google Workspace accounts.
  • Multi-factor authentication (MFA) is required for every user.
  • Constraints: data stay in the US; the platform runs on any major cloud provider.
  • Attributes involved: security (high), deployability and simplicity (high), usability (medium), interoperability (medium).

Options

OptionNotes from the ADROutcome
1. Build sign-in in the API applicationThe team writes and maintains password storage, MFA and each single sign-on integration, using libraries.Not chosen
2. Self-hosted open-source identity serverFor example, Keycloak, run as a new container.Fallback
3. Hosted identity serviceFrom a company independent of the cloud host (for example, Auth0). The identity services of cloud providers themselves are excluded, because they tie the platform to one provider.Chosen
4. Google sign-in for everyoneClient staff do not have Google accounts from Continuum.Excluded

Decision

  • Sign-in is delegated to an identity component through the OpenID Connect standard. The API application accepts only signed sign-in tokens from that component and stores no passwords.
  • The identity component provides platform accounts with MFA required; single sign-on with a client's own identity provider, set up per client when that client requires it; and Google Workspace sign-in for Continuum staff.
  • The MVP starts with option 3, a hosted identity service, provided the chosen service keeps user data in the US and its price fits the budget. If no service meets both, option 2.
  • Options 2 and 3 both use OpenID Connect, so moving from one to the other later changes configuration, not the platform's code.
  • Authorization stays in the platform. After sign-in, the API application checks the user's projects and permissions (UC-07, UC-08), including the rule that a user without any project cannot enter.
  • The specific service is chosen after checking US data location, MFA and single sign-on support, and price.

Attributes

GainedSacrificed
  • Security (high): the platform stores no passwords. MFA and single sign-on come from a component built for that purpose. For clients with single sign-on, and for Continuum staff, access ends automatically when a person leaves their organization.
  • Deployability and simplicity (high): no sign-in code to write and maintain; with a hosted service, no new container.
  • Usability (medium): client staff with single sign-on use their work account; Continuum staff use their Google account.
  • Interoperability (medium): OpenID Connect and the single sign-on standards are what client identity providers already support.
  • Deployability and simplicity (high), partly: one external service to configure, and a single sign-on setup with the IT department of each client that requires it.
  • Security (high), partly: user names and email addresses are kept by a third party. Mitigated by the US data location requirement and by keeping all project data and permissions in the platform.

Consequences

  • C1 gains three external systems: the identity service, client identity providers (for clients with single sign-on) and Continuum's Google Workspace. If option 2 is used instead, the identity server becomes a container in C2.
  • UC-07: the sign-in method is resolved.
  • For users who sign in with their organization's account, MFA is enforced by that organization's identity provider; this is confirmed per client.
  • Continuum's Google Workspace must require two-step verification for staff who use the platform.
  • The hosted service has a subscription price, compared when the service is chosen.
  • Moving between hosted and self-hosted later requires migrating user accounts; users with platform accounts may need to reset their passwords.
