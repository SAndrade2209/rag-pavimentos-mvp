Part III. Decisions

7. Decisions overview

Each architecture decision is recorded as an ADR in docs/architecture/adr/, named YYYY-MM-DD-title.md. Every ADR has the same parts: context (forces, constraints and options considered), decision, attributes gained, attributes sacrificed and consequences. Seven ADRs are accepted. Two were replaced on 2026-11-23 and are summarized in Section 9.

7.1 Reading order

The ADRs are presented so that each one relies only on the ones before it: first the documentation method, then who can enter, which client's data they see, how data arrive, how the model is reached, how answers are grounded, and last the structure of the backend that holds all of it. ADR 4 takes its expected number of clients from ADR 3; ADR 6 builds on ADRs 3 and 5; ADR 7 lists ADRs 2 to 6 as already fixed. ADRs 6 and 7 were revised together and refer to each other for the retention of answer logs. The numbers 1 to 7 are this reading order; in the repository, ADRs are identified by file name.

Reading the matrix

  • Security is gained in five of the six ADRs. ADR 4 accepts a partial cost: the platform holds access to one client system, which has to be protected.
  • Deployability and simplicity carries a cost in every ADR from 2 to 7, partly offset where the same ADR also gains it, for example no new container in ADRs 2 and 5 and one database for all clients in ADR 3.
  • Performance, a medium priority, is the attribute most often given up: ADRs 3, 5, 6 and 7 each accept a cost to it.
  • Recoverability is shaped by ADRs 3 and 7. Both note that restoring one client's data on its own is harder with a shared database.
