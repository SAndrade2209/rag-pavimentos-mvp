8.5 ADR 5. Replaceable language model interface

Put the language model behind a replaceable interface
Accepted 2026-11-23 · docs/architecture/adr/2026-11-23-language-model-behind-replaceable-interface.md
What it does

Places one small interface between the platform and any language model. Only the question answering module calls it, and each model option is an adapter behind it, selected in configuration. Moving between a hosted and a self-hosted model means one new adapter and a setting, and the interface is the single point where client data can leave the platform toward a model.

Why this option

It keeps a model switch cheap without adding a container (a gateway service) or a dependency the team does not control (a library that wraps many providers).

Context

  • UC-01 to UC-04 need a language model to interpret natural-language questions and to help write the answers.
  • Whether the model is hosted (a provider's API) or self-hosted (an open-weight model run by the team) is not decided. The platform must allow switching later without rework.
  • Constraint: language model processing stays in the US. Every model option must meet it.
  • Attributes involved: security (high), deployability and simplicity (high), extensibility (medium), maintainability (medium).

The ADR names "draft the answer from retrieved PCI rows" as an example operation. ADR 6 replaced that approach: the interface now has three operations, build a query plan, judge a plan and reword a template text, and the model receives no result rows.

Options

OptionNotes from the ADROutcome
1. Call one model provider directlyFrom wherever the code needs it. Simplest today. Switching means finding and changing every call.Not chosen
2. One small interface inside the API applicationOne implementation (adapter) per model option. Only the first adapter is built now.Chosen
3. A third-party library that wraps many model providersFor example, LiteLLM or LangChain. Switching among supported providers becomes a setting, but it adds a dependency the team does not control, and its abstractions may not fit.Not chosen
4. A separate gateway serviceBetween the API application and the model. The most flexible, but it adds a container to deploy and operate.Not chosen

Decision

  • The API application has one interface for the language model, with the operations UC-01 to UC-04 need.
  • Only the question answering module calls this interface. No other code calls a model provider directly.
  • One adapter is built, for the first model chosen. A second adapter is written only when the team switches or compares models.
  • The model and its endpoint are set in configuration, not in code.
  • A fixed set of test questions, taken from the examples in UC-01 to UC-04, with expected answers checked by a pavement engineer, is run before and after any change of model.
  • Hosted or self-hosted is decided in a separate ADR.

Attributes

GainedSacrificed
  • Extensibility (medium): switching between hosted and self-hosted takes one new adapter and a configuration change.
  • Security (high): the interface is the single point where client data leave the API application toward the model. It controls what is sent, never another client's data, and can log each call. Under ADR 6, result rows are not sent at all.
  • Maintainability (medium): prompts and model settings live in one module.
  • Deployability and simplicity (high): no new container and no new external dependency, unlike options 3 and 4.
  • Deployability and simplicity, slightly: some extra code compared with calling a provider directly (option 1).
  • Performance (medium), potentially: features specific to one provider, such as streaming an answer while it is generated, must be added to the interface explicitly before they can be used.

Consequences

  • C2: the language model container stays marked "decision pending" until the hosted or self-hosted ADR.
  • C3: the question answering module owns the interface and its adapters.
  • Every adapter must use an endpoint that processes data in the US.
  • Answers can change when the model changes. The test set is the check, so it has to be written and kept current.
  • If several models are needed at once, or routing between them, options 3 and 4 are reconsidered in a new ADR.
